# 社群数据分析面板 PRD

> 版本：V0.1  
> 日期：2026-07-30  
> 状态：讨论稿，等待确认  
> 使用者：负责观猹社群转发与数据复盘的运营人员

## 1. 产品要解决的问题

运营人员每天会向多个社群转发不同内容，但现在存在三个问题：

1. 不知道每次具体转发了什么，也缺少统一的分类和备注。
2. 转发后需要进入多个系统查浏览、访问和登录数据，复盘成本高。
3. 不同转发的统计时间不一致，无法公平比较哪类内容效果更好。

这个产品把“转发记录”和“转发后的数据表现”放在一起，让运营人员能够回答：

- 今天转发了哪些内容？
- 这些内容分别属于哪一类？
- 每次转发覆盖了哪些社群？
- 转发后前两小时获得了多少访客、浏览和登录？
- 哪种内容来源和哪个链接表现最好？

## 2. 产品结构

产品只有两个主要页面。

### 2.1 数据面板

用途：快速判断转发后的整体效果。

页面展示：

- 转发次数
- 独立访客数
- 访问会话数
- 真实页面浏览量
- 登录访客数
- 登录转化率
- 最近一次转发的增长曲线
- 最近一次转发的访问到登录转化路径
- 一次文案包含多个链接时，各链接的表现排行

这个页面主要看结果，不负责管理文案和备注。

### 2.2 详细数据分类

用途：管理每一次转发事件，并按内容来源复盘。

四种一级分类：

| 分类 | 定义 | 示例 |
|---|---|---|
| 产品方转发 | 产品团队或产品负责人提供、希望社群协助传播的内容 | 产品上新、产品更新、产品活动 |
| 观猹内容 | 观猹站内生产和发布的内容 | 站内文章、榜单、Jobs、每日上新 |
| 专业内容 | 观猹员、专业作者或行业从业者生产的内容 | 行业分析、观点文章、教程、案例 |
| 活动转发 | 以报名、参与或召回为目标的活动内容 | 沙龙、课程、黑客松、直播、招募 |

每个分类展示：

- 转发事件数量
- 独立访客总数
- 页面浏览总数
- 该分类下的全部转发记录

## 3. 记录一次转发

点击“记录转发”后，需要填写：

| 字段 | 是否必填 | 说明 |
|---|---:|---|
| 转发文案或链接 | 是 | 可以粘贴整段文案，系统自动提取其中的观猹链接 |
| 运营备注 | 否 | 记录本次转发目的、文案版本或需要后续观察的事项 |
| 实际转发时间 | 是 | 必须填写真正发到社群的时间 |
| 详细数据分类 | 是 | 四种一级分类之一 |
| 内容类型 | 是 | 产品上新、活动招募、内容分享、群公告等二级标签 |
| 社群画像 | 是 | 可以多选本次覆盖的社群 |
| 社群类型 | 是 | 核心用户群、开发者社群、课程群等 |
| 用户画像 | 是 | 普通用户、核心用户、AI 爱好者等 |
| 转发群数 | 否 | 本次实际发送的群数量 |
| 预计覆盖人数 | 否 | 用于粗略计算触达效率 |

一条转发事件可以包含多个链接。例如“每日产品上新”文案中包含 5 个产品链接，系统将其视为一次转发事件，但会分别统计 5 个链接的表现。

## 4. 数据统计口径

### 4.1 基础指标

| 指标 | 当前口径 |
|---|---|
| 独立访客 | ClickHouse 中按 `session_id` 去重 |
| 访问会话 | 按 `visit_id` 去重 |
| 页面浏览 | 只统计真实 pageview，排除组件曝光和页面心跳 |
| 登录访客 | 访问相关页面后发生登录行为的独立访客 |
| 登录转化率 | 登录访客 ÷ 独立访客 |
| 全站注册 | PostgreSQL 镜像中的同期全站注册，仅作参考，不归因到某条链接 |

### 4.2 两小时窗口

当前方案采用：

> 每次转发只比较“实际转发时间之后的前两小时”。

例如：

- 14:00 转发
- 统计窗口为 14:00–16:00
- 15:00 查看时展示 14:00–15:00 的数据
- 16:00 后数据固定，不再继续增长

采用统一两小时窗口的原因：

- 不同日期、不同发布时间的内容可以公平比较。
- 符合社群转发后重点观察 1–2 小时增长的运营习惯。
- 避免发布时间更早的内容因为累计时间长而天然数据更高。

### 4.3 需要确认的冲突

此前还提出过“链接加入面板时已经有数据，也需要显示”。

这与“只看转发后两小时增量”是两种不同口径：

| 方案 | 优点 | 问题 |
|---|---|---|
| A. 只看转发后两小时 | 能判断本次转发带来的变化，更适合横向比较 | 不显示转发前已经存在的数据 |
| B. 显示当天累计数据 | 加入面板时立刻能看到已有浏览量 | 无法证明这些数据来自本次转发 |
| C. 两套同时显示 | 既能看累计，也能看本次转发后的增量 | 页面和数据逻辑更复杂 |

当前建议采用方案 C：

- “累计数据”展示该链接当天已有的全部数据。
- “两小时增量”用于判断本次社群转发效果。
- 排名和分类比较默认使用“两小时增量”。

此项需要产品负责人最终确认。

## 5. 主要使用流程

1. 运营人员完成一次社群转发。
2. 打开面板，点击“记录转发”。
3. 粘贴完整文案，系统自动提取所有观猹链接。
4. 选择四种详细数据分类之一。
5. 勾选本次覆盖的社群画像，并填写备注。
6. 系统立即读取链接已有数据，并开始记录转发后的两小时增量。
7. 运营人员在“数据面板”观察整体增长和链接排行。
8. 运营人员在“详细数据分类”按来源复盘历史转发。

## 6. 当前版本不承诺的能力

- 无法准确判断某一个具体微信群贡献了多少访客。
- 没有渠道参数时，不能证明所有页面访问都来自这次社群转发。
- 全站注册数据不能直接归因到某条分享链接。
- PostgreSQL 镜像每日同步，不属于实时数据源。

如果后续每次转发都使用独立渠道码或 UTM 参数，可以进一步实现更准确的社群归因。

## 7. 待确认问题

1. 两小时数据是只看转发后的增量，还是同时展示当天累计数据？
2. “观猹内容”和“专业内容”的边界是否准确？观猹员原创内容应该放在哪一类？
3. 活动转发是否需要继续细分为课程、招募、直播和线下活动？
4. 是否需要为每次转发记录具体群名称，还是只记录社群画像和群数量？
5. 多位运营人员共同使用时，是否需要记录“转发负责人”？

确认以上问题后，再进入 V0.2 界面和数据口径定稿。
