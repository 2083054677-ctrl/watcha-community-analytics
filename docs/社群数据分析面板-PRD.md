# 社群数据分析面板 PRD

> 版本：V0.2
>
> 日期：2026-07-30
>
> 状态：讨论稿，等待确认
>
> 使用者：负责观猹社群转发与数据复盘的运营人员

## 1. 产品要解决的问题

运营人员每天会向多个社群转发不同内容，但转发后的数据回收依赖人工操作：

1. 转发后需要进入多个系统，分别查询浏览、访问和登录数据，复盘成本高。
2. 运营人员需要定时打开系统，分别记录实时、1 小时、2 小时和 4 小时数据。
3. 如果运营人员没有及时回收，数据容易漏记，事后也难以还原当时的增长过程。
4. 人员无法在转发消息后持续守着系统整理数据，日常执行不稳定。

这个产品的核心不是“帮运营人员记一张表”，而是：

> 运营人员只录入一次转发事件，系统自动完成后续数据回收和整理。

产品把“转发记录”“定时数据采集”和“数据表现”放在一起，让运营人员能够回答：

- 今天转发了哪些内容？
- 这些内容分别属于哪一类？
- 每次转发覆盖了哪些社群？
- 转发后实时、1 小时、2 小时和 4 小时的数据分别是多少？
- 哪种内容来源和哪个链接表现最好？
- 哪些转发任务的数据已经完整回收，哪些存在缺失？

## 2. 产品结构

产品包含两个主要页面。

### 2.1 数据面板

用途：快速判断转发后的整体效果与数据回收状态。

#### 设计目标

数据面板需要达到专业数据分析产品的呈现标准，而不是简单堆放数字卡片。页面按照“结论优先、异常突出、支持对比”的顺序组织。

#### 第一层：管理摘要

- 今日转发事件数
- 正在采集的事件数
- 已完成四小时采集的事件数
- 数据回收成功率
- 独立访客、页面浏览、登录访客和登录转化率
- 数据最近更新时间

这一层帮助管理者在 10 秒内判断：今天做了多少动作、数据是否完整、总体表现怎么样。

#### 第二层：增长过程

- 最近一次转发的 0–4 小时增长曲线
- 明确标出转发时刻、1 小时、2 小时和 4 小时节点
- 同时展示访客、页面浏览和登录访客
- 对比该分类过去转发的平均表现
- 增长明显低于历史平均时给出提醒

#### 第三层：内容效果

- 四类内容来源的效果对比
- 各分类的平均访客、平均浏览和平均登录转化率
- 一次文案包含多个链接时，各链接的表现排行
- 表现最好和最弱的内容
- 支持今天、7 天、30 天和全部历史

#### 第四层：AI 分析

- 当前转发是否仍在增长
- 与同类历史内容相比处于什么水平
- 哪个链接贡献最高
- 是否值得二次转发
- 下一次转发在内容和社群选择上的建议

页面核心指标包括：

- 转发次数
- 独立访客数
- 访问会话数
- 真实页面浏览量
- 登录访客数
- 登录转化率
- 最近一次转发的增长曲线
- 最近一次转发的访问到登录转化路径
- 多链接表现排行

这个页面主要看结果、趋势和结论，不负责管理文案和备注。

### 2.2 详细数据分类

用途：管理每一次转发事件，并按内容来源复盘。

四种一级分类：

| 分类 | 定义 | 示例 |
|---|---|---|
| 产品方转发 | 产品团队或产品负责人提供、希望社群协助传播的内容 | 产品上新、产品更新、产品活动 |
| 观猹内容 | 观猹站内生产和发布的内容 | 站内文章、榜单、Jobs、每日上新 |
| 专业内容 | 观猹员、专业作者或行业从业者生产的内容 | 行业分析、观点文章、教程、案例 |
| 活动转发 | 以报名、参与或召回为目标的活动内容 | 沙龙、课程、黑客松、直播、招募 |

每个分类展示：

- 转发事件数量
- 独立访客总数
- 页面浏览总数
- 平均登录转化率
- 数据采集完成率
- 该分类下的全部转发记录

每条记录需要展示：

- 转发时间
- 分类和内容类型
- 文案摘要与全部链接
- 运营备注
- 覆盖社群和预计人数
- 实时、1 小时、2 小时和 4 小时数据快照
- 数据采集状态

## 3. 记录一次转发

点击“记录转发”后，需要填写：

| 字段 | 是否必填 | 说明 |
|---|---:|---|
| 转发文案或链接 | 是 | 可以粘贴整段文案，系统自动提取其中的观猹链接 |
| 运营备注 | 否 | 记录本次转发目的、文案版本或需要后续观察的事项 |
| 实际转发时间 | 是 | 必须填写真正发到社群的时间 |
| 详细数据分类 | 是 | 四种一级分类之一 |
| 内容类型 | 是 | 产品上新、活动招募、内容分享、群公告等二级标签 |
| 社群画像 | 是 | 可以多选本次覆盖的社群 |
| 社群类型 | 是 | 核心用户群、开发者社群、课程群等 |
| 用户画像 | 是 | 普通用户、核心用户、AI 爱好者等 |
| 转发群数 | 否 | 本次实际发送的群数量 |
| 预计覆盖人数 | 否 | 用于粗略计算触达效率 |

一条转发事件可以包含多个链接。例如“每日产品上新”文案中包含 5 个产品链接，系统将其视为一次转发事件，但会分别统计 5 个链接的表现。

保存转发事件后，运营人员不需要继续保持网页打开。

## 4. 自动数据回收

### 4.1 自动采集节点

运营人员保存一次转发后，系统自动创建一个持续四小时的采集任务。

| 时间节点 | 系统动作 | 用途 |
|---|---|---|
| 保存时（T+0） | 读取当前累计数据并保存基线 | 识别转发前已经存在的数据 |
| T+5 分钟起 | 每 5 分钟自动刷新一次 | 绘制实时增长曲线 |
| T+1 小时 | 保存一小时正式快照 | 一小时复盘 |
| T+2 小时 | 保存两小时正式快照 | 中段复盘 |
| T+4 小时 | 保存四小时正式快照并结束任务 | 最终比较 |

### 4.2 自动回收要求

- 不要求运营人员保持网页打开。
- 浏览器关闭后，服务端仍然继续采集。
- 查询失败时自动重试，并记录失败原因。
- T+1、T+2 和 T+4 快照必须持久保存，不能只保存在浏览器中。
- 运营人员晚于实际转发时间录入时，系统根据数据库历史事件自动回填。
- 每条转发显示四种状态：采集中、已完成、部分缺失、采集失败。
- 数据面板显示整体数据回收成功率。
- 失败任务支持人工点击“重新回收”。

### 4.3 回收成功判定

| 状态 | 判定条件 |
|---|---|
| 采集中 | 尚未到达 T+4，自动任务正常运行 |
| 已完成 | T+0、T+1、T+2、T+4 快照全部保存成功 |
| 部分缺失 | 至少一个正式快照缺失，但仍可重新查询 |
| 采集失败 | 连续重试失败，无法获取有效数据 |

## 5. 数据统计口径

### 5.1 基础指标

| 指标 | 当前口径 |
|---|---|
| 独立访客 | ClickHouse 中按 `session_id` 去重 |
| 访问会话 | 按 `visit_id` 去重 |
| 页面浏览 | 只统计真实 pageview，排除组件曝光和页面心跳 |
| 登录访客 | 访问相关页面后发生登录行为的独立访客 |
| 登录转化率 | 登录访客 ÷ 独立访客 |
| 全站注册 | PostgreSQL 镜像中的同期全站注册，仅作参考，不归因到某条链接 |

### 5.2 四小时窗口

每次转发统一比较“实际转发时间之后的前四小时”。

例如：

- 14:00 转发
- 统计窗口为 14:00–18:00
- 15:00 自动保存一小时快照
- 16:00 自动保存两小时快照
- 18:00 自动保存四小时快照
- 18:00 后该次转发的比较数据固定

采用统一四小时窗口的原因：

- 不同日期、不同发布时间的内容可以公平比较。
- 同时覆盖转发后的快速响应和 2–4 小时长尾增长。
- 避免发布时间更早的内容因为累计时间长而天然数据更高。

### 5.3 累计数据与转发增量

V0.2 默认同时展示两套数据：

| 数据 | 含义 | 使用位置 |
|---|---|---|
| 当天累计 | 链接当天从 00:00 开始的全部数据 | 详情页，帮助了解内容已有热度 |
| 四小时增量 | 转发后四小时内相对 T+0 基线的增长 | 排名、分类比较和运营复盘 |

这样既不会隐藏链接已经存在的数据，也不会把转发前已有流量误算为本次转发效果。

## 6. 主要使用流程

1. 运营人员完成一次社群转发。
2. 打开面板，点击“记录转发”。
3. 粘贴完整文案，系统自动提取所有观猹链接。
4. 选择四种详细数据分类之一。
5. 勾选本次覆盖的社群画像，并填写备注。
6. 系统读取已有数据，建立 T+0 基线并创建自动采集任务。
7. 系统每 5 分钟更新增长曲线。
8. 到达 T+1 和 T+2 时，系统自动保存正式快照。
9. 运营人员随时打开“数据面板”查看结果，无需定时手工记录。
10. 运营人员在“详细数据分类”按来源复盘历史转发。

## 7. 当前版本不承诺的能力

- 无法准确判断某一个具体微信群贡献了多少访客。
- 没有渠道参数时，不能证明所有页面访问都来自这次社群转发。
- 全站注册数据不能直接归因到某条分享链接。
- PostgreSQL 镜像每日同步，不属于实时数据源。
- 如果本地服务完全关闭，当前版本无法继续执行自动采集；正式上线需要常驻服务器或定时任务平台。

如果后续每次转发都使用独立渠道码或 UTM 参数，可以进一步实现更准确的社群归因。

## 8. 待确认问题

1. “观猹内容”和“专业内容”的边界是否准确？观猹员原创内容应该放在哪一类？
2. 活动转发是否需要继续细分为课程、招募、直播和线下活动？
3. 是否需要为每次转发记录具体群名称，还是只记录社群画像和群数量？
4. 多位运营人员共同使用时，是否需要记录“转发负责人”？
5. 实时曲线采用每 5 分钟自动采集一次是否足够？

确认以上问题后，再进入 V0.3 界面和自动采集架构定稿。
